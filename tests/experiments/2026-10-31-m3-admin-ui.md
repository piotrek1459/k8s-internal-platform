# M3 UI implementation and verification plan — 2026-10-31

## Historical scope

This is an implementation snapshot and manual verification plan. The original
checklist described expected browser outcomes; it did not establish full M3
acceptance or successful private-image deployment. Current source inspection
identifies unfinished paths that the old checklist treated as targets.

The Svelte UI, Go asset embedding and UI check workflow were introduced at this
stage. The accepted [stack decision](../../docs/decisions/m3-ui-stack.md) records
the technology choice. Current startup, setup/login and healthy deployment
instructions are in the [UI guide](../../docs/user/README.md); the single entry
point is `./scripts/platform.sh up`.

## Implemented screens

Setup/login, application list and creation, application details, polled operation
progress, Secret management and credential metadata screens were introduced.
Update/scale/history/rollback/delete screens were subsequently added. Static UI
assets are built under `web/build/`, copied into the broker embed directory and
served by the Go process. Node.js is required for building, not broker runtime.

## Verification boundaries

The UI workflow installs dependencies and runs type checking, ESLint and a
production build. There is no automated browser acceptance suite. Backend tests
verify token expiry/single use, sessions and mutation protection independently of
browser navigation.

The manual acceptance targets remain:

- First-run setup at `/setup`, password confirmation and subsequent login.
- Authenticated application creation and operation progress after navigation or
  refresh, followed by an actual application HTTP request.
- Correct workload observations and revision history in the details view.
- Write-only Secret creation and explicit versioned references in app requests.
- Real private registry authentication/pulls and actionable credential errors.
- Unauthenticated access rejection, CSRF checks, logout and session expiry.

Current gaps include first-run root navigation, status JSON naming, nested error
parsing, Secret-version types, missing Secret-reference submission and the LAN
value/hostname fields. Private credential creation currently stores metadata only.
Those targets must be retested after correction; the previous procedure is not
proof that they work.

The [implementation status](../../docs/status.md) and
[test inventory](../README.md) identify the next work and evidence. The later
[healthy API lifecycle report](2026-11-08-local-workflow.md) records a real-cluster
run, while explicitly excluding automated browser-form coverage.
