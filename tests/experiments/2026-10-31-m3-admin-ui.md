# M3 — Administrator UI: manual verification procedure

This note records the documented procedure for verifying the M3 administrator UI
on the local K3s development cluster, satisfying the M3 acceptance item for
authenticated browser deployment of public and private images, verified access
controls, and persistent operation progress.

## Components built in M3

- `web/` — Svelte 5 + SvelteKit (SPA / adapter-static) + Tailwind CSS + TypeScript.
  Built static assets are embedded in the Go binary via `//go:embed`.
- `broker/internal/httpapi/ui.go` — serves `web/build/` at `/`; API paths win
  because they are registered first.
- `broker/internal/httpapi/applications.go` — `GET /api/v1/apps` list endpoint
  added (was missing from M2 implementation).
- `scripts/build-ui.sh` — builds the UI and copies assets into the broker embed dir.
- `scripts/check-ui.sh` — type-check, lint, and build (hermetic, no cluster).
- `docs/decisions/m3-ui-stack.md` — recorded Svelte 5 technology decision.

## Prerequisites

The M2 prerequisites plus Node.js 20+ and npm. Run `node --version` to confirm.

## Hermetic verification (no cluster)

```bash
./scripts/check-broker.sh    # Go tests: 91 tests, all packages
./scripts/check-api.sh       # OpenAPI contract validation
./scripts/check-chart.sh     # Helm chart lint/render
./scripts/check-ui.sh        # svelte-check + eslint + vite build
```

## Full environment spin-up with UI

```bash
./scripts/dev-env.sh up
```

This performs:
1. k3d cluster + local registry
2. Demo images built and pushed
3. Admin UI built (`scripts/build-ui.sh`) and assets embedded in broker
4. Broker container image built and pushed with embedded UI
5. Platform chart installed/upgraded
6. Port-forward to `http://127.0.0.1:8080`

## M3 acceptance walkthrough

### 1. Setup wizard

Open `http://127.0.0.1:8080` in a browser.

The app should redirect to `/setup`. The setup wizard shows a form with two
fields: bootstrap token and administrator password.

Get the bootstrap token:

```bash
./scripts/dev-env.sh token
# or from the broker logs:
kubectl --kubeconfig .local/kubeconfig -n platform-system logs deploy/platform | grep -A1 'Bootstrap token'
```

Enter the token and a password (12 characters minimum). Click "Create account".
**Acceptance:** account created → redirected to `/login`.

Expected failures:
- Wrong token → error message "token invalid or expired"
- Reusing token → 400 error (token is single-use)
- Mismatched passwords → browser-side validation

### 2. Login

Enter the password set in step 1. Click "Sign in".
**Acceptance:** session cookie set → redirected to `/apps`.

Verify CSRF protection: A POST to `/api/v1/auth/session` without the
`X-Requested-With` header returns 403.

### 3. Applications list

The `/apps` page shows an empty list with a "New application" button.
**Acceptance:** list renders with correct "No applications yet" state.

### 4. Deploy a public image

Click "New application". Follow the 6-step form:

1. **Image:** `k3d-platform-registry:5001/platform-demo:v1` (the demo image in
   the local registry after `dev-env.sh up`). Click "Inspect image".
   The digest, architecture, and suggested port appear.
2. **Application:** name `demo`, port 8080, readiness `/healthz`.
3. **Access:** Internal.
4. **Configuration:** no environment variables.
5. **Review:** confirm the settings.
6. **Deploy:** the operation progress poller polls every 2 seconds. Watch the
   stages: `running` → `applying` → `applied` → `succeeded`.

**Acceptance:**
- Operation reaches `succeeded`.
- Pod is `1/1 Running`:

```bash
kubectl --kubeconfig .local/kubeconfig -n platform-apps get pods
```

- Application detail at `/apps/{id}` shows `phase: ready`.

### 5. Verify operation progress survives navigation

While the operation is running (during long image pulls), navigate away to `/apps`
and return to the deploy step. The operation ID is preserved in component state.
**Acceptance:** operation poller re-attaches and continues showing progress.

### 6. Application detail

Click the deployed application in the list. The detail page shows:
- Status badge: `ready`
- Ready replicas: 1/1
- Workload ready: Yes
- Last successful revision: populated

### 7. Secrets

Navigate to `/secrets`. Create a new secret:
- Name: `test-secret`
- Value: any string (write-only — will not be shown after creation)

**Acceptance:**
- Secret appears in the list with its ID.
- Value is NOT shown in the API response or UI.
- Add a new version: click "Add version", enter a new value. The version count
  increases.

Attempt to delete a secret referenced by an active revision — the API returns
409 with `SECRET_IN_USE`. (Requires creating an app with a secret reference first.)

### 8. Registry credentials (private image)

Navigate to `/credentials`. Add a credential:
- Label: `test-registry`
- Registry: `k3d-platform-registry:5001`
- Username: any value
- Password/token: any value

**Acceptance:**
- Credential appears in the list.
- Selecting it in step 1 of the New Application form pre-populates the credential ID.

For a real private-image test, push a private image to an external registry
with credentials and deploy using those credentials. An invalid credential
returns an actionable error from image inspection.

### 9. Unauthenticated access

In a new private/incognito window, navigate to `http://127.0.0.1:8080/apps`.
**Acceptance:** redirect to `/login`.

Any API call without a session cookie returns 401:

```bash
curl -fsS http://127.0.0.1:8080/api/v1/apps
# → 401 Unauthorized
```

### 10. Session expiry

Sessions expire after 12 hours. After expiry, the next API call from the browser
returns 401 and the UI redirects to `/login`.

## Development workflow

To iterate on the UI without rebuilding the broker:

```bash
# Start the broker (with existing dev-env.sh up):
# Port-forward already running at :8080

# In the web/ directory:
cd web
npm run dev
# Vite dev server at http://127.0.0.1:5173
# /api/ requests are proxied to the running broker at :8080
```

Changes to `.svelte` files hot-reload instantly in the Vite dev server.
The Go broker does not need to be rebuilt during UI development.

When satisfied, rebuild for production:

```bash
./scripts/build-ui.sh        # builds web/ and copies assets to broker/internal/httpapi/ui_dist/
docker build -t localhost:5001/platform-broker:dev broker
docker push localhost:5001/platform-broker:dev
# Then upgrade the helm release:
# ./scripts/dev-env.sh up   (idempotent, re-runs the full build+install)
```
