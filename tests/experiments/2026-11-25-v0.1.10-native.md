The reference host was Raspberry Pi 5 Model B Rev 1.1, 8 GB nominal RAM
(`MemTotal: 8255680 kB`), a 31,307,333,632-byte microSD device, Raspberry Pi OS/
Debian 13.7 ARM64 and kernel `6.18.60+rpt-rpi-2712`. K3s reported
`v1.36.5+k3s1`; the installer pins Helm `v3.22.0`.

API, Kubernetes and read-only SQLite inventories matched the preceding v0.1.9
test installation: its recorded administrator/PVC/PV, one retained LAN demo,
zero configuration Secrets, registry credentials or application volumes, and
no nonterminal operations. A further controller/Pod/namespace/volume inventory

archive consistency and restoration were not verified. Prior installer state/tools
were preserved. No user application or data was identified or reset.

The unmodified published installer then installed v0.1.10 fresh. Both the desired
and actual running ARM64 platform image matched the release manifest. No published
binary, chart or installer was patched. The workstation's existing LAN leaf/key
was supplied directly to the new TLS Secret; the LAN CA private key remained on
the workstation. This was a new installation, not an upgrade of the old account
or database.

## Healthy lifecycle and trusted LAN access

The native lifecycle runner passed browser invalid-token refusal/setup/login,
bundled v1/v2 deployment, scale 2/0/1, digest-stable Pod restart, deliberately
unhealthy-v3 restoration to v2, explicit rollback and deletion with history.
The ordinary five-minute unhealthy-update timeout was allowed to complete.

An isolated Linux Chromium client reached the Pi directly using explicit hosts
resolution and normal NSS trust of the private CA. An initial untrusted-CA request
was refused. Accepted phases used no certificate-ignore/SPKI flags, protocol
overrides or HTTPS-error bypass. Global workstation hosts/trust were unchanged.
The workflow verified:

- Actual v1/v2 HTTPS, scale 2/0/1, restart and rollback.
- Tracked LAN-to-Internal, Internal-to-LAN and LAN hostname changes, matching
  effective API URLs and actual HTTPS/404 results for added/removed routes.
- Hostname validation, duplicate/history reservations, normal login and Secure/
  HttpOnly/SameSite=Strict host-only cookies absent on application origins.
- Application-origin CORS/CSRF refusal and full browser inspection/deployment of
  unprivileged Nginx, URL reload, real HTTPS content and deletion/history.

## Forced restoration and verification failure

A complete native run passed all three transitions: Internal to LAN, LAN to
Internal, and LAN hostname change. Disjoint `recovery-*` hostnames prevented
interference with the healthy demo's retained rollback reservations.

Each case observed the actual unhealthy candidate and changed route state before
temporarily restricting the recorded broker Role. UID/resource-version guards
protected changes, original rules were recorded before activation, and a bounded
host watchdog provided guarded cleanup. Deployment reads were denied to force
restoration preparation failure. The failed candidate, active operation and 409
mutation guards survived an actual broker replacement with the original API
session and metadata PVC.

Deployment reads were then restored while Ingress enumeration remained denied.
Supported recovery could apply a healthy predecessor but could not verify it;
the application remained blocked despite actual predecessor HTTP v1. A second
broker replacement preserved that state. After the exact original permissions
were restored, supported version-guarded recovery finished the same operation as
failed/restored and released its lock. The first case used normally trusted
Chromium's **Retry recovery** action and browser-side logout.

All six replacements changed broker Pod identity while retaining the original
session/PVC. Exact frozen image, Secret references, chart version/content digest,
values hash, frozen timestamp and restart identity were unchanged. The original
failed Helm Secret UID/payload remained intact. Its candidate values occurred
once in Helm history, proving that retry did not execute that candidate again.
Candidate-only environment/Secret/pull fields were cleared, the predecessor route
or its absence was verified, and Service UID/address remained unchanged.
Each owned app and its Secret/credential were removed through the supported API
with platform history retained. Original Role rules were restored. The final
test restart annotation was removed under identity/version guards, and the
resulting cleanup replacement retained its original session.

## Controlled native disclosure failures

Temporary native CEL admission policies were limited to the application namespace
and controlled object names, with explicit denial reasons, positive server-side
dry-run checks, recorded UIDs/owner labels and a bounded cleanup watchdog.
No disposable-cluster webhook/PVC fixture or production test endpoint was installed.
The native API supports these scoped policies and dry-run validation; the
[Kubernetes 1.36 admission-policy reference](https://v1-36.docs.kubernetes.io/docs/reference/access-authn-authz/validating-admission-policy/)
describes their binding and denial behavior.

Real failures were forced at configuration-Secret creation, registry-authentication
Secret creation, Helm release-Secret creation and Deployment update. Known raw
and encoded controlled values appeared in the upstream denial body, while the
platform response/history remained safe. Supported recovery resolved both blocked
Helm operations after their causes were removed.

Controlled raw/base64/authentication/configuration encodings were absent from
ordinary/history/diagnostic responses, decoded Helm payloads including persisted
failed descriptions, raw broker logs, and the actual SQLite/WAL/SHM files. The
read-only file scan checked all three files and found the expected metadata
positive control. Policies/bindings, application, Secret versions and credential
were physically removed. The accepted run completed all phases with exit 0.
This finite matrix does not prove arbitrary output safe, rewrite historical
errors, or establish a new native private-registry pull benchmark.

## Retention, reboot and final cleanup

The published same-version installer was rerun without a LAN option. Original
administrator, HTTPS API/browser sessions, both retained apps/revisions/history,
PVC/PV, TLS Secret, LAN configuration hash, workload/route identities and specs
were retained. Actual HTTPS v1 remained available.

A changed boot ID confirmed a real reboot. Direct CA-verified readiness recovered
automatically at **64.659 seconds in the outage monitor**, before SSH reconnection
or any manual service start. Original saved sessions and identities/specs were
then verified again. This is one functional startup observation, not a calibrated
timing result.

The temporary Internal app was deleted with history retained. Final API and
read-only SQLite inventory confirmed one healthy LAN demo, zero configuration
Secrets/registry credentials/application volumes, and zero nonterminal operations.
One intentional installation TLS Secret remains. Temporary policy/Role faults,
test scripts/control files and restart annotation were removed. Saved persistence
cookies were revoked/deleted; root proxies, SSH master/control directory and local
forwards were closed. The only checked listener among 80/443/8443/18080/19001 was
the intended explicit private IPv4 listener on 8443.

## Failed attempts and observations retained

Failed validation commands remain distinct from accepted phases:

- Two read-only reset guards stopped on incorrect helper assumptions about the
  gateway name and the PV's `local` form. K3s remained active; the guards were
  corrected from live/chart evidence before the owned reset.
- The first setup probe used an old auxiliary proxy's previous-cluster CA and
  failed before account creation. Only that proxy was replaced before the passing run.
- An immediate removed-route assertion received a non-error response; its exact
  status/body was not retained. The live Ingress was absent and five subsequent
  fresh requests returned 404. A resume guard then incorrectly expected a LAN URL
  on the now-Internal app. The complete repeat recorded 404 on its first removed-
  route probes, about 0.03 seconds after its operation checks. Initial propagation
  duration remains unknown. Kubernetes resource absence does not acknowledge
  synchronous data-plane reload or establish uninterrupted exposure changes.
- Recovery probes initially assumed a Deployment annotations map existed. Another
  attempt completed browser recovery but its separate Node HTTP logout client
  lacked Chromium's CA trust; the temporary cookie was revoked and its log header
  redacted. A later rename probe correctly received 409 because the healthy demo's
  rollback history already reserved that hostname. Owned partial cases were
  resolved through supported recovery/deletion, and the complete disjoint-host
  matrix subsequently passed. No SQL rows or Helm records were manually edited.
- A disclosure metadata probe used an unsupported Secret-detail URI instead of
  the documented list. Other attempts outlasted the observer/fault lease, so a
  missing scan and a removed policy failed acceptance. Owner-guarded cleanup was
  checked. A separate timed admission probe completed in about two seconds. Fresh
  observer checks, bounded longer fault leases, stage logs and atomic scan-request
  publication preceded the full passing run. Earlier commands remain failed.
- A fresh direct HTTPS login probe after cleanup timed out waiting for response
  headers. Subsequent readiness/app requests returned 200 and a fresh login returned
  204 in about 0.29 seconds without a protocol/certificate bypass. Its exact cause
  remains unconfirmed. The earlier v0.1.9 rollout-adjacent browser timeouts likewise
  have no confirmed cause or claimed fix; reproducibility/availability belongs in
  the controlled evaluation.
