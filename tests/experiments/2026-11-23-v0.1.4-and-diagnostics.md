## Subsequent diagnostics and drift implementation

The candidate source adds authenticated `GET /apps/{id}/logs`, `/events` and
`/drift` plus an application-details Diagnostics view. These additions are not
part of the published v0.1.4 binary tested above.

Log reads verify namespace/release ownership and Deployment → ReplicaSet → Pod
controller UIDs. The chain is checked again after reading to reject Pod-name
reuse. Only the application container is selectable. Reads are bounded by lines,
time, bytes, object counts, request deadlines and concurrency. Events are matched
to verified current resource UIDs. Managed configuration/registry Secret values
and supported encodings are masked in memory before text clipping; overlapping
matches and truncated prefixes are covered. Missing redaction inputs fail closed.
The UI renders text through escaped Svelte interpolation; failure screenshots
mask diagnostics text surfaces as well as inputs.

Drift compares the frozen desired chart/values snapshot with owned workload and
route fields. Reports contain field paths and classifications without expected
or actual values. Readiness and allocated addresses are separate from intent.
Inspections write no resources and reject an intent change during the read.
Redaction, retention and capacity limits are explicit in the
[API guide](../../docs/user/api-reference.md#application-diagnostics).

## Service merge-key failure and guarded explicit repair

The new real-cluster test deliberately changed a Service port from 80 to 81.
Helm's strategic three-way merge retained the changed entry and attempted to add
the desired port with the same `http` name. Reapply and compensation failed with
a duplicate Service-port name and correctly retained `needs_attention`.

Explicit Reapply now normalizes that owned ClusterIP Service's desired port list
with JSON Patch tests for UID and resource version before Helm applies the frozen
target. Service identity and allocated addresses remain unchanged. Pending Helm
transactions and changed ownership refuse preparation; preparation failure
retains a durable block. Ownership guards cover old and target manifest resources,
including removed routes, restoration and uninstall. Recovery does not bypass the
same guard. Diagnostic GETs never invoke these mutations.

The first diagnostics fixture run was rejected by the namespace ResourceQuota
because its copied-label Pod omitted CPU/memory requests and limits. The fixture
was corrected to use the existing app's resource policy. This was a harness
failure; the subsequent Service merge failure was a product defect. Failed and
interrupted exploratory runs are not accepted as passing evidence.
