## Request continuity and broker independence

During the separate 75-second, five-request/s observation, a healthy application
update and UID-guarded broker-Pod replacement were induced. The app returned
**373/375 successful requests**, with every status,
error and expected v1/v2 body retained. The original API session worked after the
replacement. The deliberately interrupted management readiness route returned
352/375; its outage is separate from
the application trace and from steady-state load.

The two failures were one HTTP 502 and one three-second client timeout, both
after update readiness and before broker replacement. Client scheduling remained
valid. The later broker outage produced no application failures. The native
five-second hook and passing CI/source samples therefore do not establish the
required zero-error published rollout. The exact endpoint/proxy/process cause
has not been established; a longer arbitrary sleep is not a verified fix.
The original failed trace remains the acceptance result. It is not replaced by
passing source/CI observations or classified as client saturation. These results
also do not establish the cause of older browser/login timeouts. Initial route
creation/removal still uses bounded convergence; Pod readiness is not synchronous
gateway acknowledgement.

Surviving Kubernetes events place the old Pod's `Killing` event approximately
five seconds before the failed requests. This is consistent with a shutdown/
routing race, but does not prove it: no simultaneous EndpointSlice watch or proxy
backend trace was collected. The read-only events and explicit unconfirmed-cause
record are retained in `retention/rollout-diagnostics.json`.
