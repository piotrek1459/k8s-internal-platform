# Local M0–M1 verification — 2026-10-14

## Scope and environment

This experiment verifies the initial application chart and manual lifecycle in a
local, single-node K3s cluster. Local development and local image storage were
selected for this implementation stage. The experiment does not constitute
Raspberry Pi validation or a public-hosting acceptance test.

The procedure is defined in [local-development.md](../../docs/local-development.md).
The final run followed cluster deletion and recreation with Secret encryption
enabled. The independent multi-architecture builder was stopped before this run.

## Results

| Check | Outcome |
| --- | --- |
| Go endpoint and configuration tests with race detection | Passed |
| Go vet | Passed |
| Hardened container execution | UID/GID 65532, read-only root filesystem, successful HTTP requests, and clean SIGTERM shutdown verified |
| Helm lint and rendering | Passed |
| Invalid chart configuration rejection | Nine cases retained in `check-chart.sh`; additional schema cases verified during chart review |
| Kubernetes server-side dry-run | Deployment, Service, and Ingress accepted under restricted Pod Security admission |
| Initial deployment | v1 became ready and served its version through the private route |
| Healthy update | v2 replaced v1 and served the expected version |
| Unhealthy update | v3 started with zero restarts, passed startup, and produced HTTP 503 readiness events; Helm reported a failed upgrade after the configured timeout |
| Availability during failed update | The private route continued to serve v2 |
| Explicit recovery | Helm rollback to revision 2 completed; the resulting release served v2 |
| Entrypoint isolation | The private hostname returned HTTP 404 through the separate `web` listener |
| Published socket bindings | API and HTTP listeners bound to `127.0.0.1` only |
| Secret encryption | K3s reported encryption enabled |
| Kubeconfig preservation | Default kubeconfig SHA-256 was identical before and after local cluster deletion; current context remained `minikube` |
| Multi-architecture packaging | Each v1/v2/v3 OCI archive contained Linux ARM64 and AMD64 manifests, with matching image configuration architectures |

The final state contains one ready v2 application pod with zero restarts. No
broker or administrator interface is implemented at this stage.

## Observed durations and resource snapshots

| Scenario | Duration |
| --- | --- |
| v1 installation and route verification | 4 s |
| v2 update and route verification | 10 s |
| Expected v3 upgrade failure | 30 s |
| v2 rollback and route verification | 2 s |

These values describe one functional verification run. The failed-update duration
is determined by the configured Helm timeout. Images were already imported into
the node; external pull time is excluded. No statistical performance conclusion
or manual-versus-platform comparison is supported by these measurements.

The final resource snapshot reported 1 millicore and 4 MiB for the demonstration
pod, and 111 millicores and 888 MiB for the K3s node. These are sampled values from
the local Docker environment, not peak requirements or Raspberry Pi sizing data.
Chart resource presets remain provisional.
