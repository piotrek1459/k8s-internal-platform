creation, actual HTTP v1/v2, scale 2/0/1, digest-stable Pod restart, deliberately
unhealthy-v3 restoration, explicit rollback and tracked deletion/history retention.

The separate workstation used an isolated Linux Chromium client with explicit
hosts resolution directly to `192.168.68.227:8443` and normal public-CA import

certificate-ignore flags, SPKI exceptions, protocol overrides or HTTPS-error
bypass. Global workstation hosts/trust were unchanged. The CA private key stayed
on the workstation and was not supplied to the browser client.

Accepted browser/API phases verified:

- Digest-pinned LAN v1/v2, update, scale 2/0/1, restart and rollback with actual HTTPS.
- Normal HTTPS login and Secure/HttpOnly/SameSite=Strict host-only cookies, absent

  reload and actual browser HTTPS content; temporary deletion retained history.

- Both live management/app routes returned 200 from an allowed peer and 403 from

The more extensive strict-SNI, three reachable IPv6 paths and independent-public-

## Browser observation requiring further investigation

The initial combined LAN command completed its API lifecycle assertions, then
failed its first browser `/version` assertion after rollback. That first response
was not retained, so its status/body and exact cause are unknown. A subsequent
controlled update/rollback navigation experiment received valid responses but
later timed out, including while waiting for navigation commit. This was not
established as a JSON-viewer-only issue or an HTTP/2 defect.

Fresh requests succeeded. Steady-state probes returned 25/25 expected v1
responses with default HTTP/2 and 25/25 with diagnostic HTTP/1.1. The accepted
resumed browser phase used the normal protocol configuration, recorded HTTP
responses within a bounded convergence check and received 200/v1 on its first
probe. The full Nginx UI/browser workflow then completed successfully. Earlier
failed attempts and diagnostic protocol overrides remain separate private
evidence, not complete passing runs or product fixes.

The timeout cause remains unconfirmed. Rollout-adjacent connection availability
and reproducibility remain follow-up observations for core reliability/evaluation;
these results do not establish interruption-free rolling HTTP service. No timeout
was relabelled as an HTTP success and no platform configuration was changed to
make the accepted browser phase pass.

TLS Secret UID, administrator, PVC/PV, both workloads/routes, revisions/history
and original HTTPS API/browser sessions. Actual HTTPS v1 remained available.
A changed boot ID confirmed a real host reboot. Direct CA-verified cluster
readiness returned at **19.66 seconds in the outage monitor**, before any SSH
reconnection or manual service start. K3s was active and the node Ready; original
identities/sessions/configuration and real HTTPS recovered. This is one functional
startup observation, not a calibrated timing/resource dataset.

After persistence verification, the temporary Internal application was deleted
with history retained. One healthy LAN demo remains. Final inventory found zero
configuration Secret metadata/values, registry credentials or application volumes;
one intentional installation TLS Secret remains. Saved API/browser sessions were
revoked and cookie files removed. Duplicate server leaf-key files, fixture
scripts, root proxies, SSH master/control sockets and local forwards were removed
or stopped. Private archive/evidence files remain protected.
