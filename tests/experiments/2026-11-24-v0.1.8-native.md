# Published v0.1.8 private LAN acceptance on Raspberry Pi

Recorded: 2026-11-24 (Europe/Warsaw). Follow-up to
[issue #16](https://github.com/piotrek1459/k8s-internal-platform/issues/16) and
[PR #22](https://github.com/piotrek1459/k8s-internal-platform/pull/22).

## Release and installation boundary

Normal [release v0.1.8](https://github.com/piotrek1459/k8s-internal-platform/releases/tag/v0.1.8)
was published from `b3fe210362b4a5596ff7e51780793eac17c8373c` by the successful
[manual workflow](https://github.com/piotrek1459/k8s-internal-platform/actions/runs/45386453838).
Published installer, guide and manifest matched their checksums and GitHub asset
digests. The installer verified/imported the ARM64 bundle; the live platform
Deployment matched the exact manifest image digest. No platform binary, image,
chart or published installer was patched for acceptance.

The reference host was Raspberry Pi 5 with 8 GB RAM, 32 GB microSD and 64-bit
Raspberry Pi OS/Debian 13, kernel `6.18.60+rpt-rpi-2712`, OpenSSL 3.5.7.
The IPv4 listener used `192.168.68.227:8443` with `192.168.68.0/24` permitted.
Actual workstation traffic was observed as `192.168.68.205` at the Pi. The
DHCP-assigned address remained unchanged through this reboot; router address
reservation was not configured during acceptance.

Pre-reset API, Kubernetes and read-only SQLite inventories matched only the seven
preceding owned acceptance records, including one active demo. No user
applications, registry credentials or application volumes were found. Cross-version
replacement was correctly refused. The stopped v0.1.7 installation was privately
archived with mode 0600 and gzip integrity checked. Installer state/tools were
preserved separately before fresh installation. Restoration was not tested;
these checks establish neither upgrades nor backup restoration.

The browser client was an isolated Linux container on the separate workstation,
using OS hosts entries resolving the management/application names directly to the
Pi. No SSH tunnel carried the positive LAN/browser tests. Only the public CA and
acceptance credentials were supplied to this client; PKI private keys were excluded.
The CA was imported into Chromium's normal NSS database following
[Chromium certificate management](https://chromium.googlesource.com/chromium/src.git/+/master/docs/linux/cert_management.md).
The client used Playwright 1.64.1 and Chromium 156.0.8078.4. The workstation's
system hosts file and global trust store were not modified. This verifies the
normal hosts/CA procedure, not router wildcard-DNS automation.

The unknown-SNI negative probe alone disabled client verification, requiring curl
exit 35 to distinguish server refusal from a local hostname-validation error.
All positive HTTPS probes verified the CA and hostname. The native host had no
independent public ingress controller; forged private Host/SNI refusal through a
reachable independent controller is established separately by the
[source suite](2026-11-24-private-lan.md), not claimed as this native experiment.
Public internet hosting remains M6 scope.

## Installer exit-status defect and correction

Published `install.sh --version v0.1.8 --check` printed a successful host result but
returned 1. The expression `[[ "$check" != true ]] || return` allowed the bare
`return` to inherit the preceding false condition's status. This was an actual
published-installer defect; fresh installation and same-version rerun themselves
returned 0.

The source correction returns 0 explicitly after successful read-only preflight.
Regressions verify success without downloads/state creation and propagation of a
failing preflight status. All **83 Python regressions** passed on macOS/OpenSSL
3.6.2 and Ubuntu 24.04/OpenSSL 3.0.13; shell syntax passed. The exact corrected
candidate was also executed **only with `--check`** on the Pi and returned 0.
It was not used to install or alter the published platform. A corrective manual
release and published-installer verification remain required before the next
implementation cycle. The historical first v0.1.8 release-verification failure is
recorded in the separate [source report](2026-11-24-private-lan.md#release-verification-compatibility-correction).

## Validation harness observations

An initial isolated-client attempt tried to initialize the NSS database already
created by Chromium; that private test process was stopped and the existing
database imported correctly. A subsequent immediate replica assertion raced the
status observer after scale-to-zero; bounded status convergence replaced that
assertion. Another attempt read Chromium's JSON document body as raw JSON;
acceptance now checks the actual browser response JSON. These incomplete attempts
are retained privately and do not count as complete passing runs. Application
mutations were restricted to the recorded owned fixture; no product patch or
waiver was used to bypass these checks.

Initial excluded-source application probes ran while its route was absent or
scaled to zero and returned 404. Accepted source-filter evidence first required
200 from the existing healthy route, then required 403 from the excluded peer
with and without forged headers.

## Reboot, cleanup and remaining work

The changed boot ID confirmed an actual host reboot. A direct verified-HTTPS
monitor observed the outage and healthy cluster readiness again after 63.83
seconds, before any SSH reconnection or manual service start. K3s remained
enabled/active; the node, broker and gateway were Ready. Original API/browser
sessions, administrator, both applications and revision histories, PVC/PV and
TLS Secret UIDs, route/workload identities and configuration hash matched.

After persistence verification, the temporary Internal fixture was deleted with
history retained. One healthy owned private-LAN demo remains. The saved API and
browser sessions were explicitly revoked and their cookie files removed. The
wrong-host TLS fixture and temporary Nginx workload were removed; the retained
TLS Secret is intentional installation configuration. Duplicate server-side leaf
key files and the read-only source candidate were removed. Final inventory and
temporary-proxy/SSH cleanup are recorded in the machine summary. Final inventory
confirmed one healthy app, zero configuration Secret metadata/values, registry
credentials and application volumes. Root Kubernetes proxies, SSH control/master
connections and local forwards were stopped.

M0/M3 LAN routing, HTTPS administration and persisted application URL criteria
have native v0.1.8 evidence. The current cycle remains open for the corrective
installer release; the next recovery/security PR does not start before that
published installer passes. The resource/evaluation cycle follows recovery.

The [machine-readable summary](2026-11-24-v0.1.8-native.json) identifies private
raw evidence by digest without publishing credentials, cookies or private keys.
Remaining core work includes worker interruption/failed-restoration/disclosure
acceptance, reference resource calibration and a controlled repeated evaluation.
A functional run and intentional Helm timeout are not a performance dataset.
